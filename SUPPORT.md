# Support boundary

Template release **v1.0.4**; see [VERSION](VERSION). This release must be qualified independently. A source release does not prove marketplace publication. This is a single-node evaluation starter with a small fixture, not HA, managed ingestion, or a production-scale warehouse. A successful job proves the tested intervals only. Budget separately for three private services, two independent 5000 MB volumes and backups; historical fixture runs are not production capacity recommendations.

- Uninitialized `prod`: the fresh default deliberately refuses to run. Use the bounded private maintenance session in [README.md](README.md), run tests, review a bounded plan and explicitly approve it. Stop maintenance and restore `./start.sh`, cron `0 * * * *`, restart `NEVER` and private/no-healthcheck settings. Never auto-apply in cron to hide initialization errors.
- Database readiness: each connection has a 10-second connect timeout and at most 12 attempts with 2-second spacing; a total invocation is finite. Confirm private DNS, port and referenced secrets. Do not open a public proxy as a workaround.
- Audit failure: job exits nonzero. Find and repair bad raw data; failed intervals remain pending. SQLMesh may have materialized data before audit failure, so never consume a newly failed physical table as approved output. Retry the interval after repair; use reviewed restatement plans for already completed history.
- Changed source: scheduled runs use persisted production snapshots until a reviewed plan promotes the change. Pause scheduling for operator plans and upgrades. Monitor job outcomes and age of the latest successful daily interval, not an HTTP healthcheck.
- Cron overlap: Railway does not start the next scheduled run while the prior run remains active. This daily fixture is small; tune workload batching before extending it. Restart is `NEVER` by contract.
- Job evidence: the runner exits and has no continuously running instance between jobs. `SUCCESS` / `buildOnly` and database readiness do not prove native SQL job success. Inspect native job logs/outcomes and persisted intervals; distinguish an actual hourly scheduler firing from a manual exact-deployment restart.
- Credentials: generated passwords are independent and should remain stable across redeploys. Database-owner privileges are intentionally broad for evaluation; use narrower roles and enforce TLS according to your production security requirements.
- State/warehouse split: back up and restore **both** at a coordinated quiescent boundary. A state-only restore can claim completed intervals whose warehouse tables are absent. There is no shared filesystem or runner volume to restore.

Historical `v1.0.3` private operator/review/application, incremental results, blocking audit failure/repair, replacement and paired restoration passed. Its restored default job was observed through a manual exact-deployment restart; hourly scheduler firing and an explicit numeric exit-code field were not observed. That historical evidence does not qualify the new release. The draft tools operate offline; see [PUBLISHING.md](PUBLISHING.md) for current exact-source/stored-graph qualification gates and registry publication status.

Standard deletion plus verified zero compute and disclosed retention is the accepted cleanup boundary. Project deletion does not establish physical erasure, expired backups, completed storage retention or billing zero. No blanket security clearance is implied. The MIT grant covers newly authored recipe source only; upstream/runtime licenses and notices remain in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
